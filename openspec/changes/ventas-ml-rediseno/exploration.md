# Exploration: Ventas ML redesign (listing + fixed detail panel + KPI strip)

**What**: Explore phase for `ventas-ml-rediseno` — rebuild Ventas ML listing (frontend/src/pages/VentasML.jsx) + detail drawer (frontend/src/components/DesgloseDrawer.jsx) to match docs/design/ventas-ml/{listado,detalle}.html Stitch mockups. Backend: backend/app/routers/ml_ventas_ops.py, backend/app/services/ml_ventas_desglose/breakdown_service.py, models in backend/app/models/ml_orders_ops.py + ml_payments.py.

**Why**: User wants "all of it" from two Stitch mockups replicated: data, ordering, icons, monospace font.

## 2. FRONTEND FOUNDATION
- Icons: project standard is **lucide-react** (`^0.563.0`, already installed), NOT Google Material Symbols the mockup uses. Skill (`pricing-app-frontend`) explicitly bans emoji and mandates lucide SVGs. Every Material Symbols icon name in the mockup needs a lucide equivalent mapping (mostly 1:1: `sync`→`RefreshCw`, `warning`→`AlertTriangle`, `check_circle`→`CheckCircle2`, `search`→`Search`, `calendar_today`→`Calendar`, `print`→`Printer`, `inventory_2`→`Package`, `open_in_new`→`ExternalLink`, `receipt_long`→`Receipt`, `content_copy`→`Copy`, `trending_up`→`TrendingUp`, `info`→`Info`, `calculate`→`Calculator`).
- Mono font: `--font-mono` token ALREADY EXISTS in design-tokens.css (`ui-monospace, "SF Mono", "JetBrains Mono", ...`) but "JetBrains Mono" is only a font-family NAME reference — not actually loaded via `@font-face`/Google Fonts link anywhere found; falls back to the OS's `ui-monospace`/SF Mono/Consolas. The mockup explicitly loads JetBrains Mono from Google Fonts. To match "the monospace font" literally, need to add the Google Fonts (or self-hosted) import — small, isolated CSS-only change.
- Design tokens: project uses `--bg-*`, `--text-*`, `--spacing-*`, `--radius-*` (Tesla system) PLUS a newer `--cf-*` Cloudflare-dark-first token set (see skill). Mockup is Tailwind-generated with its own ad-hoc Material-3-ish palette (`primary #004e9f`, `surface #f9f9f9`, semantic greens/reds as raw hex) — NOT using either existing token system. Faithfully cloning "the icons per thing" and exact colors as literal hex would violate the NEVER-hardcode-colors rule (`pricing-app-design` skill) and deepen the already-measured primitive drift (Engram obs #1261: 56 CSS modules each hand-roll `.input`, 3 competing button mechanisms, zero enforcement). Recommend mapping mockup's semantic colors (success green, error red, warning amber, info blue) onto existing `--success/--error/--warning/--brand-primary` tokens rather than copying literal hex — visually near-identical, but token-compliant.
- Dark mode: mockup is light-only; app requires both themes (hard project rule). Every new color must route through tokens so dark mode "just works" — cannot literally copy Tailwind's light-mode-only palette.
- Detail presentation: mockup A shows the detail as an inline right-side PANEL (xl:w-420px, always visible next to table) — current impl uses the SAME "drawer" word but `DesgloseDrawer.jsx` is a `role="dialog"` MODAL OVERLAY (`.overlay`/`.drawer` with focus-trap, Escape-to-close) — mockup B shows a fixed 560px slide-over with backdrop blur (closer to current modal pattern). The two mockups DISAGREE with each other on drawer type (inline panel vs. overlay slide-over) — this is a real open product decision, not a technical one.

## 3. PERFORMANCE
- Listing already paginates server-side (`PAGE_SIZE`, `offset`/`limit` params) up to 200 rows per existing convention (memory: bulk-query rule, `compute_neto_by_order_ids` batches by order_ids, never per-row).
- Adding: thumbnail (new join/call), city (from shipment JSONB — needs column promotion or JSONB extraction at query time), substatus label, coupon amount — all can be added to the SAME batch query/join, no N+1 risk IF implemented via existing batch pattern; risk is real only if implemented naively per-row.
- KPI strip aggregates (sum of neto/gauss/markup over the FULL FILTERED set, not just the visible page) is the expensive one: Total Gauss and Neto are computed live via `deducciones.calcular_total_gauss` per order (see `total_gauss` column docstring: "NOT served from this column... always recomputed live") — aggregating that over potentially 1000+ filtered orders server-side would be a new, non-trivial aggregation query or require materializing `total_gauss` reliably for sums (the column exists but is explicitly a sort key only, marked `total_gauss_stale`-prone). This needs its own design decision: either (a) SUM the stored `total_gauss` column with a staleness disclaimer, or (b) compute on-the-fly only over the current page and label "de esta página" instead of the global total the mockup implies. Flag as OPEN DESIGN QUESTION, not just implementation detail.
- Search bar ("buscar por orden, producto, SKU o comprador") needs indexed columns (`order_id` already indexed; `seller_sku`/`title` are indexed/unindexed respectively on `ml_order_items_ops` — title is not indexed, ILIKE search would table-scan at scale).

## 5. RISKS / OPEN PRODUCT DECISIONS FOR ORCHESTRATOR TO ASK USER
1. Drawer type: the two mockups disagree (inline side panel vs. slide-over modal with backdrop). Which one?
2. KPI strip: aggregate over full filtered set (needs new aggregation query + staleness policy for Total Gauss sums) or over current page only? Are "Objetivo: 25%" and "+12,4% vs mes anterior" real targets/trends to build, or drop them (no source)?
3. Product thumbnail: acceptable to skip (no ML order-items image field) or worth an extra per-item `/items/{id}` call (rate-limit/batch cost)?
4. Buyer real name + CUIT: real name is available (`raw_order.buyer.first_name/last_name`); CUIT is NOT confirmed obtainable in this shape — build with real name, drop or defer CUIT?
5. "Factura A emitida" / invoice actions ("Descargar Factura A"): tied to the separate GBP invoice integration (obs project_gbp_invoice_pdf) — in scope for this change or explicitly deferred?
6. Card brand + last-4 masked digits: not present in captured payloads — drop, or is there another ML endpoint that exposes it (needs research, not just this data source)?
7. "Resincronizar" per-order action semantics: does this need a NEW per-order resync backend action, or should it map to the existing sweep/backfill mechanism (out of scope of the ingestion design otherwise)?
8. Search bar and Export CSV / Columnas customization: entirely new features, size/priority unclear — confirm in scope.
9. Estimated delivery date on shipment: requires confirming whether ingestion fetches `/shipments/{id}` full detail today (not verified in this pass) — needs a quick follow-up check before committing to build it.
10. Multi-account switcher / top nav (Envíos/Publicaciones/Métricas/Finanzas) / notification bell: recommend explicitly excluding as out-of-scope chrome — this app has no such surfaces and building them is a different, much larger initiative.

## 6. RECOMMENDED APPROACHES

**A. Additive-incremental (RECOMMENDED)**: Keep both existing endpoints response-compatible; add NEW optional fields (thumbnail placeholder, city, substatus, coupon_amount, buyer real name) behind existing shape, restyle FE using lucide + existing token system mapped to mockup's visual language, resolve open questions 1-2 before touching drawer type. Pros: old tests mostly still pass, easy to slice into <400-line chained PRs, lowest regression risk on a money-adjacent screen (memory: this codebase has burned itself before on money-path review gaps). Cons: several PRs, slower to "feel done".
Rough PR slices (~300-400 lines each): (1) design tokens + lucide icon swap + mono font import, no data changes; (2) listing table restyle (columns reordered, Producto column, stacked status badges) using EXISTING data only; (3) backend additive fields (city, substatus, coupon_amount, buyer real name) + FE wiring; (4) KPI strip (page-scoped, ship placeholder trend copy removed) — separate PR because it needs the aggregation design decision; (5) drawer restyle to chosen type using EXISTING breakdown/iva/gauss data; (6) drawer new sections (payment method/installments from raw_payload, envío substatus) — additive backend field extraction from `raw_payload`/`receiver_address` JSONB; (7) optional: search bar; (8) optional: thumbnail (only if item-detail fetch is approved).

**B. Full simultaneous rebuild**: Rebuild both components in one/two large PRs matching the mockups closely including all decorative chrome minus the clearly out-of-scope multi-tenant nav. Pros: matches "all of it" literally, fastest to a single demo-able state. Cons: violates the ~400-line delivery budget repeatedly, high regression risk (111 existing FE/BE tests touched at once on a money screen), conflates open product decisions (KPI aggregation, drawer type) with pure restyle work, harder to review.

**C. Visual-only reskin, no new data**: Restyle exactly what's already returned by the two endpoints today (columns/order/icons/mono font) and explicitly punt every (b)/(c)/(d) datum (KPI strip, search, thumbnails, buyer real name, payment method, substatus) to follow-up changes. Pros: smallest, fastest, zero backend risk. Cons: does not satisfy "all of it" — user explicitly asked for the data too, not just the skin.

Recommendation: **A**, starting with the token/icon/font PR (near-zero risk) then the listing restyle PR, deferring the KPI aggregation design decision and the drawer-type product decision to an explicit sdd-propose step before writing code for those two.
