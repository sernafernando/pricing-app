# Spec: Ventas ML redesign (delta spec, revision 1)

Source: proposal #2104 (rev 2) + user binding decision 2026-09-22 (sales screen product filters) + explore of `frontend/src/hooks/useProductosFilters.js` / `backend/app/api/endpoints/productos_listing.py`. Spec describes WHAT must be true after the change; no implementation mechanics.

## Capability: ml-sales-product-filters

New capability, split out from `ml-sales-search` because these are product-attribute facet filters (brand, subcategory, PM, product facets that describe the SALE (never today's catalog state)), not free-text search — `ml-sales-search` (R25) already extends its `q` matching to item title and seller SKU, which is search, not a facet.

### Requirements

- R35 The sales listing and the KPI aggregation accept, through the same shared filter builder used by every other Ventas ML filter (KPI R7), the following product-level facet filters, ported from the Productos screen's equivalent filters: brands (`marcas`), subcategories (`subcategorias`), PMs (Product Managers, resolved via their assigned marca+categoría pairs).
- R36 Each product-level facet filter matches a sale when it matches the sale's underlying frozen order-item cost snapshot (`ml_order_item_costos`), joined to the product catalog (`productos_erp`) via `ml_order_item_costos.producto_item_id`. Brand and subcategory filter on `productos_erp` fields directly; PM filters via the `marca`+`categoría` pairs assigned to the selected PM users (same resolution `productos_listing.py` already uses).
- R36a The OFFICIAL STORE filter is OUT of scope, for the same verified reason as R37: a sale's store can only be read from the product's CURRENT publications (`productos_erp.item_id` → `tb_mercadolibre_items_publicados`), so the same sale would match or stop matching as publications move. That is today's catalog state, not the sale (R40). Revisit only if the store is stored per sale at ingestion time.
- R37 The sales screen does NOT offer a publication-status filter. VERIFIED against the schema: `tb_mercadolibre_items_publicados` carries no MLA column (only `item_id`), so Productos' own `estado_mla` means "this PRODUCT has at least one active publication today" (productos_listing.py ~835-850), never the status of the MLA that was sold. Applied to a sale it would describe the product's current catalog state, which is exactly the class of filter R40 rules out. If a per-sale publication status is ever wanted, it needs the status stored at sale time (see the separate note about ML publication states not being persisted).
- R38 A sale matches when ONE OF ITS ITEMS matches EVERY active product facet at once (user decision 2026-09-22). Facets are NOT evaluated independently: a pack holding a Lexmark printer and an Epson cartridge does NOT match "marca=Epson AND subcategoría=Impresoras", because no single item matches both. For a pack, the whole group is returned when any ONE of its items satisfies all active facets.
- R39 An order-item with no frozen cost row (no `producto_item_id`) can never satisfy a product facet, and it never removes its sale from results where no product facet is active: with no product filter, a sale whose only item is unresolved is still listed and still counted by the KPI.
- R40 The following Productos-screen filters are explicitly OUT of scope for this screen because they describe the product's state TODAY, not the sale: stock, con precio, web transferencia, Tienda Nube, colores, con/sin MLA (presence toggle), nuevos últimos 7 días (recency of the product record), auditoría.
- R41 Any markup/rebate/oferta-style filter on this screen (if offered) MUST be computed from the sale's own frozen cost and price (`ml_order_item_costos`: `costo_unitario_ars`, `precio_unitario`, `iva_pct`), never from `ProductoPricing` (live pricing) — a live-pricing-derived filter would contradict what actually happened at sale time. If a markup/rebate/oferta filter cannot be expressed this way, it is out of scope for this screen.
- R42 Promotion/PxQ-style filters (the ones resolved cross-DB against the mlwebhook database via `_resolve_and_fold_mlas`) are explicitly DEFERRED, not shipped by this change: they only reflect the promotion's CURRENT state, never the sale's historical promo state at the time of purchase, and reconciling that gap is out of scope here.
- R43 `ml_order_item_costos.producto_item_id` MUST have a dedicated index, created by its OWN migration shipped and deployed in a SEPARATE, earlier PR than the one adding the joins that cross it. Every product-facet filter crosses that column, the listing pages up to 200 rows and the KPI aggregates the whole filtered set.

### Scenarios

1. Given a pack whose items are from two different brands, when the user filters by one of those brands, then the pack (and every member order, including the item from the OTHER brand) appears in both the listing and the KPI aggregation (R38).
2. Given a product-level filter (e.g. a subcategory) that matches none of a sale's items, when results return, then that sale/pack is excluded from both the listing and the KPI aggregation (R38, negative case).
3. Given a combined filter of brand + subcategoría + date range + the four doubtful-case toggles, when the user applies it, then the listing and the KPI aggregation agree on exactly the same filtered set (parity, same guarantee as KPI R14, now including product-level facets).
4. Given an order-item that has no matching `ml_order_item_costos` row (no `producto_item_id`), when the user applies an UNRELATED product-level filter that a sibling item in the same pack DOES match, then the sale/pack still appears — the unresolved item contributes nothing but does not cause the sale to be silently dropped (R39).
5. Given the same order-item with no frozen cost row, when the user applies a product-level filter directly (e.g. that exact brand), then that order-item alone never causes a match on its own (R39, direct case).
6. Given a request asking for a publication-status filter, when the shared builder parses it, then it is ignored as out of scope (the API defines no such parameter, so the request succeeds with the remaining filters applied) (R37): no sale is filtered by the current status of its product's publications.
7. Given a request carrying an official-store parameter, when the shared builder parses it, then it is ignored exactly like the publication-status parameter (R36a, R37): the API defines no such filter, so the response is a normal 200 with the remaining filters applied, never a silent filter by today's catalog.
8. Given the user attempts a markup filter on this screen, when it is implemented, then it reads `ml_order_item_costos` frozen cost/price fields exclusively — a code review or test asserting it never joins `ProductoPricing` passes (R41).
9. Given a request for a promo/PxQ filter on this screen, when the design is reviewed, then it documents the filter as explicitly deferred with the historical-state reason (R42) — no promo/PxQ param exists on the sales endpoints in this change.
10. Given no product facet is active, when the listing and the KPI run, then a sale whose only item has no `producto_item_id` is returned and counted like any other (R39).
11. Given `marcas` and `subcategorias` are BOTH active, when a pack holds one item matching only the brand and another matching only the subcategory, then the pack is NOT returned; when a single item matches both, the whole pack is returned (R38).
12. Given a product facet carries an invalid value (non-numeric id, empty entry), when the request is parsed, then it fails with HTTP 422 and never degrades into "no filter"; the same rule applies identically to the listing and the KPI.
