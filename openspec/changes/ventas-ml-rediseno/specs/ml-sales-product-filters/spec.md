# Spec: Ventas ML redesign (delta spec, revision 1)

Source: proposal #2104 (rev 2) + user binding decision 2026-09-22 (sales screen product filters) + explore of `frontend/src/hooks/useProductosFilters.js` / `backend/app/api/endpoints/productos_listing.py`. Spec describes WHAT must be true after the change; no implementation mechanics.

## Capability: ml-sales-product-filters

New capability, split out from `ml-sales-search` because these are product-attribute facet filters (brand, subcategory, PM, official store, current publication state), not free-text search — `ml-sales-search` (R25) already extends its `q` matching to item title and seller SKU, which is search, not a facet.

### Requirements

- R35 The sales listing and the KPI aggregation accept, through the same shared filter builder used by every other Ventas ML filter (KPI R7), the following product-level facet filters, ported from the Productos screen's equivalent filters: brands (`marcas`), subcategories (`subcategorias`), PMs (Product Managers, resolved via their assigned marca+categoría pairs), official store (`tienda_oficial`).
- R36 Each product-level facet filter matches a sale when it matches the sale's underlying frozen order-item cost snapshot (`ml_order_item_costos`), joined to the product catalog (`productos_erp`) via `ml_order_item_costos.producto_item_id`. Brand and subcategory filter on `productos_erp` fields directly; PM filters via the `marca`+`categoría` pairs assigned to the selected PM users (same resolution `productos_listing.py` already uses); official store filters via the product's published MLA(s), same official-store definition the Productos screen uses (`build_filtro_tiendas_oficiales_mla`, including its `sin_tienda` token).
- R37 The sales screen does NOT offer a publication-status filter. VERIFIED against the schema: `tb_mercadolibre_items_publicados` carries no MLA column (only `item_id`), so Productos' own `estado_mla` means "this PRODUCT has at least one active publication today" (productos_listing.py ~835-850), never the status of the MLA that was sold. Applied to a sale it would describe the product's current catalog state, which is exactly the class of filter R40 rules out. If a per-sale publication status is ever wanted, it needs the status stored at sale time (see the separate note about ML publication states not being persisted).
- R38 A PACK (group of sub-orders sharing a `pack_id`) matches a product-level facet filter (R35-R37) when ANY of its member order-items matches — the same any-item-matches semantics the existing promo filter uses for packs (design D12 group semantics: "filter selects GROUPS; ANY member matches; all members returned"). A single (non-pack) order is itself the only member of its own group for this purpose.
- R39 An order-item with no frozen cost row (`ml_order_item_costos.producto_item_id` unresolved, i.e. no matching row for that order/item) cannot match ANY product-level facet filter (R35-R37) on its own — it contributes nothing toward making its sale/pack match those filters. It MUST NOT be silently excluded from an UNRELATED filter's results because of this: a sale/pack with at least one item that matches an active product-level filter still appears, even if a sibling item in the same pack has no frozen cost row.
- R40 The following Productos-screen filters are explicitly OUT of scope for this screen because they describe the product's state TODAY, not the sale: stock, con precio, web transferencia, Tienda Nube, colores, con/sin MLA (presence toggle), nuevos últimos 7 días (recency of the product record), auditoría.
- R41 Any markup/rebate/oferta-style filter on this screen (if offered) MUST be computed from the sale's own frozen cost and price (`ml_order_item_costos`: `costo_unitario_ars`, `precio_unitario`, `iva_pct`), never from `ProductoPricing` (live pricing) — a live-pricing-derived filter would contradict what actually happened at sale time. If a markup/rebate/oferta filter cannot be expressed this way, it is out of scope for this screen.
- R42 Promotion/PxQ-style filters (the ones resolved cross-DB against the mlwebhook database via `_resolve_and_fold_mlas`) are explicitly DEFERRED, not shipped by this change: they only reflect the promotion's CURRENT state, never the sale's historical promo state at the time of purchase, and reconciling that gap is out of scope here.
- R43 `ml_order_item_costos.producto_item_id` has a dedicated index supporting every product-level facet filter join (R35-R37); this index ships as its own Alembic migration, applied before any PR that adds a join against it.

### Scenarios

1. Given a pack whose items are from two different brands, when the user filters by one of those brands, then the pack (and every member order, including the item from the OTHER brand) appears in both the listing and the KPI aggregation (R38).
2. Given a product-level filter (e.g. a subcategory) that matches none of a sale's items, when results return, then that sale/pack is excluded from both the listing and the KPI aggregation (R38, negative case).
3. Given a combined filter of brand + subcategoría + date range + the four doubtful-case toggles, when the user applies it, then the listing and the KPI aggregation agree on exactly the same filtered set (parity, same guarantee as KPI R14, now including product-level facets).
4. Given an order-item that has no matching `ml_order_item_costos` row (no `producto_item_id`), when the user applies an UNRELATED product-level filter that a sibling item in the same pack DOES match, then the sale/pack still appears — the unresolved item contributes nothing but does not cause the sale to be silently dropped (R39).
5. Given the same order-item with no frozen cost row, when the user applies a product-level filter directly (e.g. that exact brand), then that order-item alone never causes a match on its own (R39, direct case).
6. Given a request asking for a publication-status filter, when the shared builder parses it, then it is rejected/ignored as out of scope (R37): no sale is filtered by the current status of its product's publications.
7. Given the official-store filter set to a specific store, when a sale's frozen item resolves (via `producto_item_id` → `productos_erp` → its published MLA(s)) to that store, then the sale appears, using the identical official-store resolution the Productos screen uses (R36).
8. Given the user attempts a markup filter on this screen, when it is implemented, then it reads `ml_order_item_costos` frozen cost/price fields exclusively — a code review or test asserting it never joins `ProductoPricing` passes (R41).
9. Given a request for a promo/PxQ filter on this screen, when the design is reviewed, then it documents the filter as explicitly deferred with the historical-state reason (R42) — no promo/PxQ param exists on the sales endpoints in this change.
