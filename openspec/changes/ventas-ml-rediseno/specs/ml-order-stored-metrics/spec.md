# Spec: Ventas ML redesign (delta spec, revision 2)

Source: proposal #2104 (rev 2) + explore #2103, with binding decisions Q1-Q3 resolved by the user, and design.md revision 2 (binding user decision: no cron, no global `before_commit` hook; column-scoped DB triggers enqueue into a versioned dirty queue + `pg_notify` inside the writer's transaction; a dedicated `pricing-worker` LISTENs and recomputes asynchronously). Spec describes WHAT must be true after the change; no implementation mechanics.

## Capability: ml-order-stored-metrics

### Requirements
- R1 Every ML order has a stored metrics record with explicit fields: `total_gauss` (nullable), `neto`, `neto_sin_iva`, `markup`, and a `status` enum of at least `ok`, `provisional`, `unresolved`.
- R2 Per-field NULL rules (never a silent zero, no fabricated number): `total_gauss` (and `markup_pct`, which derives from it) MUST be NULL if and only if `gauss_status = unresolved`; it MUST be non-NULL for `gauss_status = ok` or `gauss_status = provisional`. `neto` MAY be NULL independently of `gauss_status`, and only when there are no relevant payments to compute it from; such orders MUST be reported as `unknown` (never as `0`) by any reader, including KPI sums (which track an `unknown_count` alongside the sum). An order with no `ml_order_metrics` row at all (not yet computed) is in the distinct `pending` state — it MUST NOT be represented as a row with NULL-valued fields, and readers MUST treat `pending` the same way they treat `recalculating` (R3): excluded from KPI sums, never shown with a stale or fabricated value.
- R3 Every write path that changes an input to the Total Gauss calculation (payments, refunds, frozen cost, Flex shipping cost, "% de varios" config, repairs/backfills, per-order resync) MUST cause the order to be enqueued for recompute in the same transaction as the input write. The stored metrics record MUST be recomputed from the committed inputs and become consistent with a fresh recompute within approximately 1 second of that commit. Until the recompute lands, the order's state is explicitly `recalculating`: it MUST be excluded from all KPI sums (with a visible count of how many orders are excluded) and MUST NEVER be displayed anywhere with its prior/stale value presented as current or good.
- R4 A backfill process populates stored metrics for all pre-existing orders. A divergence check (stored vs. freshly recomputed) MUST report zero divergence before any reader is switched to stored values.
- R5 After the switch, listing, detail panel, and KPI aggregation read ONLY the stored values; none of them recompute Total Gauss/neto/markup live.
- R6 The detail panel's displayed breakdown chain total MUST always equal the stored `total_gauss` for that order when the order is not `recalculating` (invariant, not just visually similar). While an order is `recalculating`, the detail panel MUST show an explicit recalculating indicator instead of asserting the chain-equals-stored invariant.
- R7 No cron job (scheduled OS-level or application-level periodic script triggered by crontab/cron-equivalent) is introduced by this change to drive metrics recompute, backfill, or divergence checking. Recompute is driven by transactional enqueue + asynchronous worker notification, with a bounded-interval safety poll and scheduled in-worker jobs as the only periodic mechanisms; none of them is a cron job.
- R8 After deployment, every stored metrics record computed under an older `formula_version` than the current one MUST be recomputed automatically (without a manual script) before it is treated as authoritative. For every order, the stored values MUST equal the values produced by the live computation chain (divergence check reports zero divergence for that order) before readers are switched to rely on it.

### Scenarios
1. Given an order whose payment is newly approved, when the payment-ingestion write commits, then the order is enqueued for recompute in that same transaction; within approximately 1 second the stored `total_gauss`/`neto`/`markup`/`status` are updated and equal a fresh recompute; until that update lands, the order is reported as `recalculating` and excluded from KPI sums.
2. Given an order with a stored `status=ok` metrics record, when a refund is registered against it, then the order is enqueued for recompute in the same transaction as the refund write, the stored record is recomputed from the committed refund within approximately 1 second, and if the refund makes an input unresolvable, `status` becomes `unresolved` and `total_gauss` becomes NULL (never a stale or zero number, and never shown as good while `recalculating`).
3. Given an order with unknown/missing frozen cost, when metrics are computed, then `status = unresolved`, `total_gauss = NULL`, and the UI never displays a fabricated total.
4. Given an order still awaiting a resolvable input (e.g. pending exchange rate), when metrics are computed, then `status = provisional` and `total_gauss` holds the best-effort provisional value, distinguishable from `ok`.
5. Given the "% de varios" configuration changes, when the change is applied, then every order whose Total Gauss depends on that config is enqueued for recompute via a single set-based operation covering all affected orders, each such order is shown as `recalculating` until its recompute lands, and no order is left indefinitely stale or silently unrecomputed.
6. Given the one-time backfill has run, when the divergence check compares stored vs. recomputed values for every order, then it reports zero divergences; if any divergence is found, readers are NOT switched to stored values.
7. Given stored values are authoritative and an order is not `recalculating`, when the detail panel renders the Total Gauss chain, then the chain's final total equals the stored `total_gauss` field exactly (invariant test, not approximate).
8. Given a per-order resync is triggered, when the resync's writes commit, then the order is enqueued for recompute in that same transaction, and the stored metrics record is recomputed from the committed resync data within approximately 1 second; while pending, the order is reported as `recalculating`, never as a stale prior value presented as current.
9. Given no evidence exists for a metric (unresolved), when any reader (listing, detail, KPI) displays that order, then it shows an explicit "unresolved" indicator — never an invented number, never silently omitted from context that would let it be misread as zero.
10. Given a concurrent write lands on an order while its recompute is already in progress, when the recompute finishes, then the order is re-enqueued (not lost) and is recomputed again so the stored record reflects the latest committed inputs, never a value that ignores the concurrent write.
11. Given the recompute worker process is down, when input writes keep committing, then the recompute queue depth grows, affected orders remain `recalculating` indefinitely, and the UI displays an explicit "Recálculo detenido" state (worker considered not alive) rather than presenting any order as freshly computed; a health signal exposes the queue depth and the age of the oldest pending item.
12. Given a `pg_notify` (or equivalent wake signal) is missed (e.g. due to a worker restart or reconnect), when the periodic safety poll runs, then any order left dirty is still picked up and recomputed without requiring a missed notification to be resent.
13. Given a single order's recompute keeps failing (e.g. due to bad data), when it has failed a bounded number of consecutive attempts (parked), then it is excluded from further automatic recompute attempts, is counted and visible in health/observability output, and its failure does NOT block or delay recompute of any other order. A recompute that never completes because the worker process dies (or can no longer signal liveness) while handling it counts as a failed attempt, so an order that repeatedly kills the worker is also parked and cannot stall the queue. A parked order stays parked across periodic reconcile/backfill passes (the parked count does not flap); only a new write to one of its inputs makes it eligible again. An order is only charged a failed attempt for its own failure: when a group of orders is processed together and the group as a whole exceeds its time bound, no order in it is charged, and each is retried on its own.
14. Given the deployed formula for Total Gauss changes (bumping `formula_version`), when the deploy completes, then every order whose stored metrics were computed under an older `formula_version` is automatically recomputed (no manual script required), and the divergence check reports zero divergence for those orders once recompute completes, before readers rely on the stored values as authoritative.
15. Given this change is implemented, when its recompute/backfill/divergence mechanisms are inspected, then no cron job (OS-level or application-level scheduled script) exists anywhere in the delivered implementation driving them.
16. Given the worker is alive and processing a long backlog (e.g. the initial backfill), when the backlog takes longer than the liveness threshold to drain, then the worker is still reported as alive (and as draining), and the UI does NOT show the "Recálculo detenido" state. This holds even when a single unit of recompute work (one batch or one long computation) runs longer than the liveness threshold or the claim lease: liveness depends only on the worker process being alive, never on how long any unit of work takes, and a slow but alive worker's in-progress orders are never counted as failed attempts nor reclaimed by another worker. If the worker loses its ability to signal liveness, it stops and is restarted rather than continuing unobserved.
17. Given two recompute attempts of the same order overlap (e.g. a slow worker whose claim expired and a second worker that re-claimed it after a newer input write), when the attempt based on the older inputs finishes last, then it MUST NOT overwrite the stored metrics produced from the newer inputs; the stored record reflects the latest committed inputs, or the order remains `recalculating` until it does.
