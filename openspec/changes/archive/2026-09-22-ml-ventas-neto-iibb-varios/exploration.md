# Exploration: ML sales net — SIRTAC add-back, débitos/créditos withdrawal tax, "% de varios" on net-of-IVA amount

**What**: Explored the ML-ventas net/IVA/total-gauss pipeline to scope two business-rule corrections: (1) VariosDeduccion must apply "% de varios" to `monto_operacion` (gross WITH IVA) instead of `neto_sin_iva`; (2) SIRTAC IIBB withholding (`tax_withholding_sirtac-<prov>`) must stop being subtracted from `neto` (add back `net_amount(charge)`, post-refund) while `sirtac_sobretasa`, `collector` (débitos/créditos) and unmatched "Retención" keep subtracting.

**Why**: User-requested correction to the ML sales money path; current rule (base="neto" applied to neto_sin_iva, and SIRTAC subtracted like every other withholding) misrepresents the seller's real deductible base and double-penalizes SIRTAC which ML already treats as a pass-through credit, not a real cost.

**Where** (call chain, all in backend/app/services/ml_ventas_desglose/):
- `payment_effective_net` (breakdown_service.py:842) — computes `neto` from `net_received_amount` + refund correction. This is the ONE place to add back SIRTAC (or a parallel function), consumed by `compute_breakdown` (922), `compute_neto_by_order_ids` (860), and `descomponer_neto` (iva.py:170, via import).
- `descomponer_neto` (iva.py:170) builds `componentes` (ComponenteIVA list) per charge; SIRTAC currently hits the `charge.type == "tax"` branch (line 345-371) as `_passthrough(bruto)` with `bruto = -net_amount(charge)`, subtracted into `suma_bruto` which must equal `neto` exactly (`reconcilia`). **CRITICAL COUPLING**: if `neto` is increased by the SIRTAC amount but the componente still contributes `-amount` to `suma_bruto`, reconciliation breaks by exactly that amount. The SIRTAC componente must become informational (contribute 0 to `suma_bruto`/`neto_sin_iva`) while still carrying its display amount — `ComponenteIVA` currently has no "informational" flag; needs one, or a parallel list.
- `calcular_total_gauss` (deducciones.py:424) consumes `neto_sin_iva_by_order` (only value, no `monto_operacion`) and applies `VariosDeduccion.base=="neto"` → `objetivo = neto_sin_iva`. To switch the base to `monto_operacion`, that value must be plumbed in — it does NOT exist in this bulk pipeline today. `monto_operacion` (compute_breakdown, sum of `MlOrderItemOps.unit_price*quantity`, WITH IVA) is a DIFFERENT source than iva.py's "Venta" componentes (built from `MlOrderItemCosto.precio_unitario*quantity`, a frozen/cost-basis snapshot table, despite the label "Venta" — needs confirming in design whether these two are meant to be equal or are genuinely distinct concepts).
- `VariosDeduccion` (deducciones.py:299-367) — docstring explicitly defends `base="neto"` and claims it matches `calcular_comision_ml_total`'s `varios_porcentaje` usage (backend/app/services/pricing_calculator.py:242, a SEPARATE forward-pricing estimate, NOT part of this change — do not touch it, only rewrite the comparison in this docstring).
- `persistir_total_gauss` (deducciones.py:606) / `refrescar_total_gauss_pendientes` (574) / `marcar_stale` (552) — persist stored `total_gauss` column on `MlOrdersOps`; recompute happens only via `refrescar_total_gauss_pendientes` (batch, `MAX_TOTAL_GAUSS_REFRESH_PER_PASS=500`/pass) driven by `total_gauss_stale`/`total_gauss_at IS NULL`. To force recompute of ALL existing prod rows after deploy without a new cron job: run `marcar_stale`-equivalent UPDATE (`total_gauss_stale=True` for all rows) once via existing admin/migration path, then let the existing sweep (already scheduled) drain the backlog — needs confirming which existing job calls `refrescar_total_gauss_pendientes` and its cadence, to size the drain time for ~all prod orders.
- Refunds: `net_amount(charge) = amount - refunded` already used everywhere (breakdown_service.py:765-769); the "add back only non-refunded SIRTAC" requirement is satisfied for free by using `net_amount(charge)` (not raw `charge.amount`) for the add-back — same pattern already used for every other charge in this module.
- `is_seller_charge` (breakdown_service.py:751) returns True for tax-type/SIRTAC charges (only excludes `coupon`/`bonus` types, `financing_fee` name, and names containing "payer") — so SIRTAC is already inside `seller_charges` used everywhere, including refund math in `payment_effective_net`.
- Frontend precedent already exists for "shown but not subtracted" lines: `DesgloseDrawer.jsx` filters `breakdown.lines` by `line.origen !== 'propio'` (line 266) to keep Flex's real freight cost visible without double-counting it against `neto` (it's genuinely subtracted only in the Total Gauss chain). This `origen` field is the natural mechanism to reuse for marking the SIRTAC line informational — likely needs a new `origen` value (not "propio", which is Flex-specific) so SIRTAC renders in a comparable side-channel, not inside the neto-subtraction list. Response building in `routers/ml_ventas_ops.py` (`obtener_operacion:1147`, `listar_ventas:809`) was not read in this pass — needs a follow-up read to confirm origen/line shape end-to-end before design.
- Tests pinning current behavior: `backend/tests/services/ml_ventas_desglose/test_iva.py` (26 tests), `test_deducciones.py` (39), `test_breakdown_service.py` (56), `test_tax_labels.py` (9), `test_billing_warning.py` (4) — 134 total, several will need rewriting (SIRTAC reconciliation, VariosDeduccion base, `TestTheTwoPathsToTheNetAgree` must still hold after both changes since `compute_breakdown` and `compute_neto_by_order_ids` must apply the SAME new SIRTAC rule).
- Fixtures: `backend/tests/fixtures/ml_charges` (with withholdings) — not yet inspected line-by-line, needs a real fixture with SIRTAC + refund to write the regression test (project convention: fixtures captured, not invented).

**Learned**:
- The reconciliation invariant (`neto == sum(componentes.bruto)`, `reconcilia` flag) is the single biggest coupling risk — any change to `neto` computation (payment_effective_net) MUST be mirrored by an equal-and-opposite change to descomponer_neto's per-charge componente construction, or every order's IVA breakdown starts reporting `reconcilia=False`/a nonzero `diferencia` in production.
- `monto_operacion` (compute_breakdown, MlOrderItemOps-based) and the "Venta" IVA componentes (descomponer_neto, MlOrderItemCosto-based) are two independently-sourced item-price computations that happen to usually agree but are NOT the same code path — VariosDeduccion's new base needs one of them wired into the total_gauss bulk pipeline, which currently only carries `neto_sin_iva`.
- `calcular_comision_ml_total`/`varios_porcentaje` (pricing_calculator.py) is a distinct forward-pricing estimate feature and must NOT be touched — only its docstring cross-reference inside VariosDeduccion needs updating.
- Recompute-after-deploy for stored `total_gauss`: no new cron allowed (user policy); rely on marking existing rows stale and letting the ALREADY-SCHEDULED sweep (source job not yet located) drain up to 500/pass.
- Suggested wording risk: since "Neto" will now exceed what ML actually deposits (by the SIRTAC add-back), the UI label needs a caveat (e.g. tooltip "no incluye retención IIBB SIRTAC, acreditable") — flag for design/propose, not resolved here.

**Rough PR slicing (~400 lines each, each safe standalone)**:
1. iva.py: add informational-line support to `ComponenteIVA`/`descomponer_neto` for SIRTAC (no behavior change yet — additive field, tests for new shape) — foundation PR.
2. breakdown_service.py: `payment_effective_net` add-back of non-refunded SIRTAC + wire the informational flag through `compute_breakdown`/`compute_neto_by_order_ids`; update `TestTheTwoPathsToTheNetAgree` and reconciliation tests. This is the actual money-path behavior change — highest risk, smallest safe scope.
3. deducciones.py: VariosDeduccion base switch to `monto_operacion`, plumb the value through `calcular_total_gauss`/`persistir_total_gauss`; update docstrings and `test_deducciones.py`.
4. routers/ml_ventas_ops.py + DesgloseDrawer.jsx/VentasML.jsx: response shape + informational-line rendering (new `origen` value), label/tooltip wording for "Neto".
5. Ops/migration: mark all `MlOrdersOps.total_gauss_stale=True` (or equivalent) to trigger recompute via the existing sweep; no new cron.
